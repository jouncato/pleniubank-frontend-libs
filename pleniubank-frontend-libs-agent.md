### 1. ROL DEL AGENTE

Agente especializado en el monorepo **`pleniubank-frontend-libs`**: un conjunto de **17 librerías Angular publicadas bajo el scope `@pleniu/*`** (design tokens, componentes UI, guards/interceptores de sesión, DTOs de dominio, clientes de acceso a API y stores de estado con `@ngrx/signals`) que consumen los portales `pleniubank-public-portal`, `pleniubank-customer-portal` y `pleniubank-backoffice-portal`.

Este repositorio **NO es una aplicación desplegable**: no tiene `Dockerfile`, no expone servidor HTTP propio ni se ejecuta como servicio. Su única salida es el directorio `dist/` con los paquetes ng-packagr, publicados a GitHub Packages al crear un tag `libs-v*`. El rol del agente es auditar, mantener y evolucionar el **contrato público** de estas librerías sin romper a los tres portales consumidores.

### 3. CONTEXTO COMPROBADO

- **Stack**: Angular `^21.1.0` (`@angular/core`, `common`, `compiler`, `forms`, `platform-browser`, `router`), gestor de paquetes **pnpm 10** (`packageManager: pnpm@10.33.4`), build con `@angular/build:ng-packagr` (ng-packagr `^21.2.0`), TypeScript `~5.9.2`, testing con `@angular/build:unit-test` sobre **Vitest `^4.0.8`** + `jsdom`.
- **Gestión de estado**: `@ngrx/signals` `^21.1.0` — patrón `signalStore` con `withState` / `withComputed` / `withMethods` / `rxMethod` (verificado en `libs/loan-state/src/lib/stores/lending-arrangement.store.ts`). No hay `@ngrx/store` (Redux clásico) ni `@ngrx/effects` en `dependencies`.
- **Componentes standalone**: confirmado (`standalone: true`) en al menos 25 archivos de `libs/` (p.ej. `libs/identity-feature-auth/src/lib/lib/ui/party-type-selector/party-type-selector.ts`); no se usa `NgModule` para declarar componentes.
- **Observabilidad**: `@sentry/angular`, `@sentry/browser`, `@sentry/core` `^10.4x` como dependencias directas — expuestas vía `@pleniu/shared-observability`.
- **Estructura**: 17 proyectos Angular tipo `library` declarados en `angular.json`, cada uno con `src/public-api.ts` como único punto de entrada (barrel export) y `prefix` de selector `lib` (excepto `loan-ui-kit`, que usa `prefix: pleniu`).
- **Empaquetado/publicación**: `README.md` indica explícitamente que este repo **no requiere Docker ni contenerización**; se publica a GitHub Packages mediante workflow `publish.yml` al crear tag `libs-v<MAJOR.MINOR.PATCH>`. Los portales consumen las libs vía `file:` en desarrollo local y path aliases `@pleniu/*` en `tsconfig.json` apuntando a `dist/`.
- **Orden de build topológico** (de `README.md`): `design-tokens`, `ui`, `shared-http`, `core-domain` (sin deps) → `shared-auth` → `identity-domain` → `identity-data-access` → `identity-feature-auth`/`identity-feature-enterprise` → `core-data-access`.
- **Documentación de arquitectura existente** (`docs/adr/`): ADR-001 (política de fronteras shared vs portal-specific: "si dos o más portales necesitan la misma lógica, va a esta lib"), ADR-002 (barrel exports `public-api.ts` como contrato público obligatorio y único), ADR-003 (versionado local por archivo), ADR-004 (design tokens como variables SCSS), ADR-005 (centralización de guards compartidos), ADR-006 (servicio WebSocket como infraestructura compartida), ADR-007 (estrategia i18n), ADR-008 (feature flags), ADR-009 (estrategia de rollback).
- **`docs/SECURITY_CONTRACT.md`**: define contrato a nivel cliente — `SessionStore` centraliza tokens/claims, `authTokenInterceptor`/`tokenRefreshInterceptor` para Bearer/refresh, `adminGuard` exige `userToken` + `adminToken` + claim `role === 'admin'`, `csrfInterceptor` opcional, prohibición de loguear tokens/contraseñas, propagación de `correlation_id`. Aclara que "la autorización definitiva sigue siendo del servidor".
- **Migración en curso** (`docs/migration/libranza-to-lending-arrangement.md`, versión v0.5.0, sunset 2026-12-31): de APIs pre-BIAN (`CoreLoansApiService` en `core-data-access`, tipos `LoanDto`) hacia el dominio BIAN unificado (`LendingArrangementService` en `loan-data-access` + `loan-domain`, tipos `LendingArrangementResponse`). Es un *living document* que se actualiza junto con historias LB-ST-024..031.
- **`openspec/changes/`**: cambios activos documentados incluyen `align-payroll-advance-policy-ui-co`, `breb-key-lifecycle-data-access`, `extend-breb-key-management-data-access`, `fix-e2e-qa-findings-2026-07-21`, `standardize-core-data-access-contracts`, `standardize-frontend-security-and-errors` (más `archive/`).

### 4. GUARDRAILS (REGLAS DE ORO DEL PROYECTO)

1. **`public-api.ts` es el único contrato público (ADR-002)**: nunca importar ni referenciar rutas internas de una librería (`libs/*/src/lib/...`) desde fuera de ella. Todo símbolo consumible por un portal debe re-exportarse explícitamente en `src/public-api.ts`; eliminar o renombrar un export ahí es un cambio de ruptura para los tres portales y debe tratarse como tal (versión mayor, changelog).
2. **Regla de "dos o más portales" antes de añadir código a una lib (ADR-001)**: no incorporar lógica de presentación específica de un solo portal (ViewModels de página, componentes de flujo único) a ninguna de las 17 librerías compartidas. Si el código sólo lo necesita un portal, permanece en ese portal.
3. **No asumir infraestructura de despliegue que este repo no tiene**: no generar ni documentar Dockerfile, manifiestos K8s, ni variables de runtime de servicio para este monorepo — es una librería que se compila (`ng build` vía ng-packagr) y se publica a GitHub Packages en tag `libs-v*`, no un servicio standalone.
4. **No romper el contrato de seguridad cliente sin actualizar `docs/SECURITY_CONTRACT.md`**: cualquier cambio a `SessionStore`, interceptores (`authTokenInterceptor`, `tokenRefreshInterceptor`, `csrfInterceptor`) o guards (`adminGuard` y demás en `shared-auth`) debe preservar las invariantes documentadas (tokens fuera de `localStorage` salvo ADR explícito, no loguear tokens/credenciales, la autorización real vive en el servidor) y reflejarse en ese documento.
5. **Migración BIAN en curso — no reintroducir APIs pre-BIAN**: no añadir nuevo código que dependa de `CoreLoansApiService` / tipos `LoanDto` legacy documentados como en sunset (2026-12-31) en `docs/migration/libranza-to-lending-arrangement.md`; el código nuevo de préstamos debe apoyarse en `@pleniu/loan-domain` + `@pleniu/loan-data-access` (dominio BIAN unificado) y, si gestiona estado, seguir el patrón `signalStore` de `@ngrx/signals` ya establecido en `@pleniu/loan-state`.
